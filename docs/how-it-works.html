How Face Match Works

A plain-language, visual walk through the whole project: how a photo becomes a searchable fingerprint, how Qdrant stores it, how exact search and HNSW find the closest face, and how the graph behind HNSW is built.

1The big picture

Face matching turns the question "is this the same person?" into a geometry problem: every face becomes a point in space, and similar faces land close together.

Two jobs, one pipeline

Enrolling a person: run steps 1-4 and store the vector with a name or ID. Searching: run steps 1-4 on a new photo and ask Qdrant for the closest stored vectors. Only the last step differs.

1:N and 1:1

1:N identification (who is this among everyone enrolled?) is what we tested. 1:1 verification (are these two photos the same person?) is just one cosine comparison, no database needed.

Where the work happens

The models run on your Mac through ONNX Runtime. Only the vector database (Qdrant) lives in a container inside Colima, a small Linux VM that runs Docker on macOS.

2Detecting and aligning the face

The recognizer is picky: it expects an upright face, centered, at a fixed size. Getting there takes two steps.

SCRFD: "where is the face?"

The file scrfd_10g_bnkps.onnx is a detector. For every face it returns a box, a confidence score, and 5 landmark points: both eyes, the nose tip and both mouth corners ("bnkps" = box + keypoints). It does not rotate or crop anything.

Alignment: "make it standard"

Code (face_align.norm_crop) takes those 5 points and finds the rotate + scale + shift that moves them onto a fixed template. Then it warps the picture into a 112×112 crop. Eyes always end up level and in the same spot.

Why alignment mattersSkip it and the same person photographed at a slight tilt looks like a different point in space. Many "bad matches" are really "badly aligned" matches. The benchmark images we used (VGGFace2 112×112) were already aligned, so detection was skipped there; real photos need the full pipeline.
What about the other model files?2d106det and 1k3d68 find denser landmarks, genderage guesses gender and age. None is needed for matching, so the project only uses scrfd_10g_bnkps and glintr100.

3Embeddings: a face becomes a point

The recognition model glintr100 is a deep neural network trained on millions of faces to do one thing: photos of the same person should produce nearby points; different people should produce distant points.

An embedding is a list of numbers

For each face the model outputs 512 numbers. You can picture it as coordinates of a point in a 512-dimensional space. Nobody can draw 512 dimensions, but the idea is the same as a dot on a 2D map: closer = more alike.

The numbers have no names

No single number means "nose width" or "eye colour". The meaning is spread across all 512 and was learned by training. What matters is only the relative distance between points.

Normalization

Each vector is scaled to length 1 ("L2 normalized"), so only its direction matters, not its size. This is what makes cosine similarity (next section) simple and fair.

Simplified to 2 dimensions. Searching = "which stored cluster is the new photo closest to?"

4Cosine similarity: how "close" is measured

To compare two faces we look at the angle between their vectors. A small angle means the vectors point the same way, so the faces are alike.

Angle: 35°Cosine: 0.82Match %: 82%

Reading the value

1 = identical direction (same face). 0 = unrelated (right angle). Negative = opposite. For real faces, different people typically land low and the same person lands noticeably higher.

Why angle and not distance?

Normalized vectors all have length 1, so they sit on the surface of a sphere. The straight-line distance and the angle are tied together, and cosine is cheap: one dot product.

"Match %" is not a probability

We show cosine × 100 as "match %" for readability. 45% does not mean "45% chance it is the same person". It is a similarity score, and the threshold that separates "same" from "different" has to be chosen by testing.

5Qdrant: the vector database

A normal database answers "find rows where name = X". A vector database answers "find the stored vectors nearest to this one". Qdrant does that, quickly, and keeps the data on disk.

Collection

A named table of vectors that share the same size and distance rule. Ours: 512 numbers each, cosine distance.

Point

One stored item: an ID, the vector, and an optional payload (extra info such as the person's name, the image path, merchant ID).

Segments and the optimizer

Qdrant stores points in chunks called segments. In the background an optimizer decides when a segment is big enough to be worth indexing and builds the search index for it.

Docker + Colima

Qdrant ships as a Docker container. Docker needs Linux, so on a Mac Colima runs a tiny Linux VM that hosts it. Our code talks to it over localhost:6333.

Cosine inside QdrantWhen a collection uses cosine distance, Qdrant normalizes each vector as it is stored. After that, comparing two vectors is just a dot product, which is very fast.

6Two ways to search: exact and approximate

"Index" simply means an extra structure built ahead of time so that searching later is faster. The two approaches trade accuracy against speed.

Exact search (flat / brute force)

no index The vectors sit in a plain list. For each query the database compares the query with every stored vector and keeps the best few.

  • Always returns the true nearest faces.
  • No build step, no tuning.
  • Work grows in step with the collection size: double the faces, double the work.

Perfect for small collections and for use as a ground truth to check an approximate method against.

Approximate search (ANN) e.g. HNSW

index built first A navigation structure is prepared so a query only visits a small neighbourhood of promising vectors instead of all of them.

  • Much faster at large sizes.
  • Usually finds the true nearest, but can occasionally miss.
  • Has settings to trade speed for accuracy, and costs memory and build time.

"ANN" = Approximate Nearest Neighbour.

Important detail about QdrantQdrant only builds the HNSW index once a collection grows past a size limit (indexing_threshold). Below that it quietly does exact search. In this project the small test collections were effectively exact until we forced the index on.

7HNSW: the graph, step by step

HNSW = Hierarchical Navigable Small World. Read the name backwards: a small world network that you can navigate, organised in a hierarchy of layers.

The graph: nodes and edges

A graph is just dots joined by lines. Every stored face vector is a node. A line between two nodes (an edge) means "these two are neighbours". Each node keeps a short list of the neighbours it links to.

How many connections?A node does not link to everyone. Each node holds only a small, capped number of links. The cap is the parameter m (Qdrant default 16) on the upper layers, and about double that on the bottom layer, which is the most detailed one. So a graph of thousands of nodes still has only a few dozen links per node. That limit keeps memory small and searching fast.

The small-world idea

Think of how you can reach almost anyone in the world through a short chain of acquaintances. Most of your friends are local, but a few know people far away, and those long-range links create shortcuts. HNSW links each node mainly to its close neighbours, plus a few links that reach further away. A search can then travel across the whole collection in a handful of hops.

The hierarchy: layers like a road map

Top layers: highways

Very few nodes, with long links between them. Used to jump quickly into the right region of the data.

Middle layers: main roads

More nodes, shorter links. Used to move closer to the target.

Layer 0: every street

Contains all the nodes with fine, short-range links. Used for the careful final search.

How a node's layer is chosen (it is random, not clustering)

Layers are not built by grouping similar faces. When a node is inserted, the algorithm rolls a weighted die. The rule makes high layers exponentially rare:

  • Almost every node lands only on layer 0.
  • A small fraction also appear on layer 1 (about one in m).
  • A still smaller fraction reach layer 2, and so on.

A node that reaches layer 2 is present on layers 2, 1 and 0. This is the same trick as a skip list: random promotion naturally produces an express lane without anyone planning it. The first node to reach the highest layer becomes the global entry point for all searches.

Inserting a new node (how links get made)

1

Roll the layer

Decide the highest layer this node will live on.

→
2

Descend

Start at the entry point on the top layer and hop greedily toward the new vector, layer by layer.

→
3

Find neighbours

On each layer the node belongs to, search for its closest nodes using a candidate list of size ef_construct.

→
4

Link

Connect to a chosen few and add the link back from them. Trim a neighbour's list if it grows past the cap.

Which neighbours get chosen? (the diversity trick)Linking to the closest few would often give you five nodes all in the same direction, which makes poor roads. HNSW uses a heuristic: take candidates from closest to farthest and keep one only if it is closer to the new node than to the neighbours already kept. The result is links that fan out in different directions, including the occasional longer one that acts as a shortcut between clusters.

Searching the graph

1

Enter at the top

Begin at the entry point on the highest layer.

→
2

Greedy hop

Move to whichever linked node is closer to the query. Repeat until no neighbour is closer.

→
3

Drop a layer

Take that node down to the next layer and repeat. The map zooms in.

→
4

Beam search on layer 0

Keep a list of the ef best candidates and keep exploring around them until nothing better turns up.

Because each hop moves closer and the upper layers do the long-distance travel, only a small part of the collection is ever examined. That is why speed barely changes as the collection grows, while exact search keeps getting slower.

Why HNSW can missThe walk is greedy. If it heads into a slightly wrong neighbourhood early on, the truly closest face may never be visited. A larger ef keeps more backup candidates alive, giving the search more chances to recover. That is the whole accuracy-versus-speed dial.

9Is the edge value the cosine?

Short answer: no, edges carry no value at all. The cosine decides who gets linked and which way to walk, but it is not stored on the line.

What an edge really is

An edge is just a pointer: "node 17 lists node 42 as a neighbour". The index is essentially a list of neighbour IDs per node per layer. There is no weight, no score, no distance saved with it.

Where the cosine is used

  • While building: to rank candidate neighbours and pick which ones to link.
  • While searching: every time the walk reaches a node it computes the similarity between the query and that node's vector, on the fly, to decide where to go next.
Why not store it?The score depends on the query. The "closeness" of two linked nodes is already recoverable from their vectors, and the useful number is always "how close is this node to today's query". Recomputing it is a single dot product, cheaper than storing and keeping weights consistent.
Two small truthsLinks are not guaranteed to be mutual: A may list B while B has trimmed A from its own capped list, so the graph is technically directed. And HNSW does not require cosine: the same structure works with dot product or Euclidean distance. Cosine is just the rule we chose for this collection.

11Other ways to do nearest-neighbour search

HNSW is the most popular choice, but it is one of several families. Each answers the same question with a different shortcut.

FamilyIdea in one lineGood atWeakness
Flat / brute forceCompare against everything.Exact, simple, small data.Slows down as data grows.
Tree-based
(KD-tree, Annoy)		Repeatedly split the space in halves; search only the relevant branches.Low-dimensional data; Annoy is light and read-only.Classic trees stop helping at hundreds of dimensions (the "curse of dimensionality").
Hashing
(LSH)		Hash vectors so similar ones tend to land in the same bucket.Very simple, cheap memory.Usually less accurate than graphs for the same speed.
Clustering
(IVF, "inverted file")		Group vectors into clusters; at query time search only the few closest clusters.Large datasets, easy to scale and shard.Misses if the answer sits in a cluster you skipped; needs a training step.
Compression
(scalar / product / binary quantization)		Store a smaller, rougher copy of each vector so more fit in memory and compare faster.Huge collections, lower RAM.Loses some precision; often paired with a re-check on the original vectors.
Graph-based
(HNSW, NSG, Vamana / DiskANN)		Link vectors to neighbours and walk the graph toward the query.Best speed-versus-accuracy for most workloads.Build time and memory for the links; hard to delete from cleanly.
What Qdrant offersQdrant's main index is HNSW. It can also compress vectors (quantization) and keep data on disk, and these can be combined with HNSW at very large scale. DiskANN-style graphs are designed for datasets bigger than RAM.

12From a score to a decision

Search returns the closest stored faces and a similarity for each. Turning that into "match / no match" is a policy choice.

accept high similarity

Top result scores above the upper cut-off. Treat as the same person. Safest zone: very few wrong names.

review the grey zone

Plausible but not certain. Send to a human or a second check. This protects against confident mistakes.

no match low similarity

Nobody enrolled looks close enough. Correct for people who were never enrolled, but also where genuine hard photos end up.

The two kinds of error

False negative (a miss). A person who is enrolled is not matched. Usually harmless: the case just goes to review.
False match (a wrong name). The system confidently names the wrong person, or accepts someone who is not enrolled. This is the costly one, so thresholds are set to keep it rare.
Raising the thresholdmakes the system more careful: fewer wrong names, but more people sent to review. Lowering it does the opposite. There is no free setting, only a trade-off that you pick based on the cost of each kind of error.

How we measured it

  • Top-1 / Top-5 / Top-10: is the right person the first result, or somewhere in the first 5 or 10?
  • Enrolled vs unknown: some test photos belong to people never stored, to check the system correctly says "not found".
  • Exact vs HNSW: same data, both searches, to see what the shortcut costs.
  • Duplicate detection: run the same search across a customer database to flag one person registered under several IDs.

The numbers themselves live in the Excel report and the charts dashboard; this guide is about how it all works.

13Things to remember

Benchmark photos are the easy caseTest faces came from a clean, pre-aligned public dataset. Real ID-photo-versus-selfie pairs are harder (age gap, lighting, small or blurry faces), so thresholds must be re-checked on real data.
LicensingThe antelopev2 model weights and the VGGFace2 dataset are for non-commercial research use. Confirm licensing before any production use.
Matching is not the same as proving it is a live personA printed photo or a screen replay can still produce a high similarity. If this is used for authentication or KYC, a separate liveness (anti-spoofing) check is needed.
